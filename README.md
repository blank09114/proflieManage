# proflieManage

의뢰인 한 명이 자작 캐릭터의 프로필과 이미지 피드를 관리하는 웹사이트다. 방문자는 메인 화면에서 콘텐츠를 열람하고, 관리자는 로그인 후 수정 화면에서 내용을 편집한다.

## 현재 상태

`react-migration` 브랜치에서 기존 HTML·CSS·JavaScript 화면과 기본 동작을 React·TypeScript로 이식했다.

- `/`에서 메인 화면, `/edit`에서 수정 화면을 확인한다. 기존 `/manage.html` 주소도 수정 화면으로 연결한다.
- 모달·피드 열기와 닫기, 클릭한 이미지 확대, 색상 미리보기, 파일명 표시, 피드와 섹션 추가·삭제, 공통 입력 검증을 React 상태와 이벤트로 처리한다.
- 선택한 이미지의 `File` 객체는 수정 화면의 편집 상태에 보관한다.
- Supabase 클라이언트와 고정 이메일 로그인, 관리자 UUID 확인, 세션 복원·변경 감지, 로그아웃을 연결했다. `/edit`과 `/manage.html`은 확인된 관리자만 접근할 수 있다.
- 메인 화면은 DB의 프로필·섹션·키워드·피드·테마를 조회한다. 목록은 저장된 순서로 표시하고, 캐릭터 이름을 페이지 제목에, 테마색을 CSS 변수에 적용한다.
- 로딩·조회 오류·재시도·빈 목록과 이미지 표시 실패를 처리한다.
- `site-edit-saving` 브랜치에서 수정 화면의 DB 데이터 채우기와 전체 저장, 프로필·피드 이미지 업로드·교체·삭제를 연결했다. 테마 편집값도 CSS 변수에 미리 적용한다.
- 저장 중 중복 요청을 차단하고, 실패하면 편집 내용을 유지한다. 다른 창에서 먼저 저장한 내용과 충돌하면 최신 데이터를 다시 불러올 수 있다.
- `editor-drag-sort` 브랜치에서 섹션과 피드 파일 제목 행의 드래그 정렬을 연결했다. 마우스·터치·키보드로 편집 순서를 바꾸고 저장 버튼으로 DB에 반영한다.
- `section-formatting` 브랜치에서 메인 화면의 섹션 내용에 볼드·밑줄·이탤릭·취소선·표 표시를 연결했다. 편집 화면과 DB에는 서식 기호를 포함한 원문을 유지한다.
- `fixes-and-refactoring` 브랜치에서 인증 재확인 중 편집 내용을 보존하고 저장을 잠그며, 미저장 변경의 화면 이탈 확인을 연결했다.
- 같은 브랜치에서 섹션·피드의 공유 드래그 잠금과 로그인 모달의 비밀번호 초기화·요청 중 닫힘 차단을 연결했다. 개선 단계별로 커밋을 나누며 PR은 전체 개선 완료 후 진행한다.
- 저장·업로드·정리 실패와 재시도를 회귀 검사로 추가하고 GitHub Actions에 린트·단위 검사·빌드·브라우저 검사를 구성했다.
- 새 이미지의 형식·용량과 피드 총 개수를 선택·저장 전에 검사한다. 실제 Storage 버킷과 저장 함수에도 제한을 적용했다.
- 메인·수정 화면은 공개 읽기 전용 `load_site` RPC로 프로필·테마·전체 목록을 한 시점의 스냅샷으로 읽는다.
- 화면과 저장 서비스의 입력 검증·키워드 파싱, DB↔편집 데이터 변환과 테마 필드 대응을 공통 유틸로 정리했다.
- 조회·취소·재시도는 `useSiteQuery`, 편집·저장·이미지 정리·이탈 보호는 `useSiteEditor`로 분리했다. 저장·정리의 동기 잠금과 인증·정렬 잠금은 유지한다.
- 모달 닫기·초점·배경 스크롤과 동작 줄이기를 보완했다. 이미지 삭제 실패 기록을 복구하고 현재 DB 참조를 확인한 뒤 정리하며, Vercel 보안 헤더와 운영 점검 절차를 준비했다.

이식 후 빌드·린트와 브라우저 동작 검증 67개를 통과했다. 390·768·1280px 화면과 긴 파일명 표시도 확인했다.

Supabase 연결 코드는 실제 SDK와 로컬 인증 테스트 서버로 브라우저 검증 19개를 통과했다. 실제 프로젝트의 환경변수를 입력하고 5개 테이블·초기값·RLS를 적용했으며, 공개 키로 5개 테이블의 API 조회를 확인했다.

메인 데이터 연결은 실제 프로젝트의 초기 데이터 표시와 테스트 데이터를 이용한 브라우저 검증 40개를 통과했다. 정렬·테마·페이지 제목·이미지 경로·빈 목록·조회 실패와 재시도, 대량 목록의 페이지 단위 조회를 확인했다.

수정·저장 연결은 브라우저 검증 33개와 저장 서비스 모킹 11개를 통과했다. 실제 Supabase에 저장 함수·Storage 정책을 적용했고, 롤백 검증으로 관리자 권한·ID 유지·순서 교환·추가/삭제·재시도·충돌·전체 롤백을 확인했다. 390·768·1280px 레이아웃과 빌드·린트도 통과했다. 이미지 업로드·삭제 HTTP 흐름은 테스트 서버에서 확인했다.

드래그 정렬은 테스트 서버에서 브라우저 검증 44개와 저장 서비스 집중 검사 6개를 통과했다. 마우스·터치·키보드 이동, 긴 목록 자동 스크롤, 빠른 목록 밖 드롭 취소, 새 항목·파일 연결 유지, 저장 후 수정·메인 화면의 표시 순서를 확인했다. 실제 DB 저장 함수도 동일 내용 행의 ID 순서 변경과 새 행 교체를 처리하도록 보완했으며, 응답 유실 재시도를 포함한 롤백 검사 후 기존 데이터가 유지됨을 확인했다.

섹션 서식은 파서 검사 28개와 테스트 서버의 브라우저 검사 37개를 통과했다. 원문 편집·저장과 메인 서식 표시, 표·중첩·이스케이프·잘못된 문법·HTML 텍스트 처리, 긴 입력, 390·768·1280px 레이아웃과 표 내부 키보드 스크롤을 확인했다. 빌드·린트도 통과했다.

퍼블리싱 원본과 상세 작업 계획은 작업 공간에서 프로젝트 루트의 형제 폴더인 `sketch/`와 `sketch/plan.md`에 둔다.


## Supabase 환경변수

프로젝트 루트의 `.env.local`에 값을 입력한다. 같은 항목을 `.env.example`에도 정리했다.

| 환경변수 | 확인 위치 |
|---|---|
| `VITE_SUPABASE_URL` | 프로젝트의 Connect 창에서 Project URL 복사 |
| `VITE_SUPABASE_PUBLISHABLE_KEY` | Project Settings → API Keys → Publishable key 복사 |
| `VITE_ADMIN_EMAIL` | 관리자 Auth 계정 이메일. `dkal1572@naver.com`으로 설정 |
| `VITE_ADMIN_USER_ID` | Authentication → Users에서 관리자 계정의 User UID 복사 |
| `VITE_SUPABASE_STORAGE_BUCKET` | 이미지용 공개 버킷 이름. 기본값은 `site-images` |

URL과 공개 키는 프로젝트의 Connect 창에서도 함께 확인할 수 있다. [Supabase 연결 안내](https://supabase.com/docs/guides/getting-started/api-keys)

`VITE_ADMIN_USER_ID`는 `supabase/schema.sql`의 `private.is_site_admin()`에 지정한 UUID와 동일하게 설정한다. 관리자 이메일·비밀번호는 Supabase Auth 사용자로 설정하고, 사이트에서는 비밀번호만 입력한다.

브라우저용 키는 Publishable key 또는 기존 프로젝트의 `anon` 키를 사용한다. Secret key와 `service_role` 키는 서버 전용이다. `.env.local`은 Git에서 제외한다. [Supabase API 키 안내](https://supabase.com/docs/guides/getting-started/api-keys)

환경변수를 저장한 뒤 개발 서버를 재시작한다. Vercel 배포 시에는 같은 환경변수를 프로젝트 설정에 입력하고 다시 배포한다.

## 공개 이미지 조회

프로필과 피드의 이미지 경로는 공개 버킷 `site-images` 안의 `profile/…`, `feed/…` 경로로 저장한다. 이 버킷을 실제 프로젝트에 생성했으며 `supabase/schema.sql`에도 생성 구문을 포함했다. 메인 화면은 DB 경로를 Storage 공개 URL로 변환해 표시한다.

수정 화면에서 이미지와 목록을 등록하면 저장한 내용과 순서가 메인 화면에 표시된다.

## 공개 콘텐츠 조회

`supabase/schema.sql`을 적용한 뒤 `supabase/read.sql`을 실행한다. 메인과 수정 화면의 `loadSite`는 `load_site()` RPC를 한 번 호출한다. 목록은 `sort_order`, `id` 순으로 반환하며, 여러 테이블 요청이나 페이지 사이에 다른 창의 저장 결과가 섞이지 않는다. 응답 전체를 확인하고 취소된 요청의 결과는 버린다.

함수는 하나의 SQL SELECT로 구성한 `STABLE`, `SECURITY INVOKER` 함수이며 `search_path`를 비웠다. `anon`, `authenticated`에 실행을 허용하고 기존 테이블 SELECT 권한과 RLS를 따른다. PostgreSQL의 `STABLE` 함수는 호출 쿼리의 스냅샷을 사용한다. [공식 스냅샷 설명](https://www.postgresql.org/docs/current/xfunc-volatility.html)

저장 시 사용하는 `private.site_snapshot()`의 `VOLATILE` 설정과 기존 `save_site` 충돌 검사는 유지한다. 다른 창의 최신 저장 내용은 새로 조회할 때 반영된다.

## 이미지 업로드 제한

- 새 파일은 JPG·JPEG·PNG만 받으며 파일당 최대 10MB(10MiB, 10,485,760바이트)다. 빈 파일은 거절한다.
- 피드는 기존 이미지와 새 선택을 합쳐 최대 50장이다. 프로필 이미지는 한 장이다.
- 선택 즉시 검사하며, 여러 파일 중 하나라도 잘못되면 그 묶음 전체를 추가하지 않는다. 기존 선택과 편집 내용은 유지한다. 저장 서비스도 모든 새 파일과 개수를 업로드 전에 다시 검사한다.
- Storage `site-images` 버킷의 `file_size_limit`은 `10485760`, `allowed_mime_types`는 `image/jpeg`, `image/png`다. 저장 RPC는 잠금 안에서 피드 총 개수를 검사한다.
- 기존 파일을 제한 초과로 삭제하지 않는다. 기존 피드가 50장을 넘으면 그 개수까지 유지·재정렬·교체할 수 있고 추가 증가는 막는다. 저장 후 개수가 줄면 다음 편집부터 줄어든 개수와 50 중 큰 값이 한도가 된다.
- 이미지 원본을 그대로 전송한다. EXIF 등 메타데이터를 제거하거나 재인코딩하지 않는다. 형식 검사는 확장자·MIME을 기준으로 한다.

버킷 제한은 `supabase/schema.sql`, 피드 개수 검사는 `supabase/save.sql`에 기록했다. 기존 프로젝트에 적용할 때는 `schema.sql` 마지막의 버킷 설정 구문과 `save.sql`을 실행한다. 피드 개수 제한은 `save_site`를 통한 사이트 저장에 적용하며, 관리자에게 허용된 직접 테이블 쓰기 권한은 별도로 유지한다.

## 수정 내용 저장

새 프로젝트에서는 `supabase/schema.sql`을 실행한 뒤 `supabase/read.sql`, `supabase/save.sql`을 실행한다. 저장 SQL에는 관리자 전용 `save_site` 함수와 `site-images` 버킷의 `profile/`, `feed/` 접근 정책이 포함된다. 다른 버킷을 사용하면 환경변수와 Storage 정책의 버킷 이름을 함께 변경한다.

섹션 위의 `↕ 순서 이동` 손잡이나 피드 파일 제목 부분을 드래그해 순서를 바꾼다. 터치로도 옮길 수 있으며, 손잡이에 키보드 초점을 둔 뒤 Space 또는 Enter로 잡고 위아래 방향키로 이동한 후 다시 Space 또는 Enter로 놓을 수 있다. Esc 키 또는 목록 밖에 놓기로 이동을 취소한다. 정렬 후 저장 버튼을 누르면 DB의 `sort_order`에 반영된다. 순서만 바꿀 때에는 이미지를 다시 업로드하지 않는다.

수정 화면은 기존 데이터와 이미지 경로를 읽는다. 새로 선택한 이미지만 고유한 경로에 업로드하고, 프로필·테마·섹션·키워드·피드의 내용과 순서를 한 번의 DB 트랜잭션으로 저장한다. 유지한 항목의 ID와 기존 이미지 경로는 보존한다. DB 반영이 성공하면 교체되거나 삭제된 기존 이미지를 정리한다.

업로드 단계에서 실패하면 DB를 변경하지 않고 미저장 파일을 정리한다. DB 요청의 응답을 받지 못하면 성공 여부가 불명확하므로 새 이미지를 보존한다. 같은 화면에서 다시 저장하면 업로드한 경로를 재사용하며, 이미 반영된 동일 요청은 중복 항목을 만들지 않는다. 결과가 불명확한 상태에서 편집을 버리거나 화면을 닫으면 미사용 업로드 파일이 남을 수 있다.

기존 이미지 정리만 실패한 경우에는 내용 저장 성공과 정리 재시도를 구분해 표시한다. 확실히 미사용인 정리 대기 경로와 대기 시각은 프로젝트·버킷별 브라우저 저장소에 기록한다. 같은 브라우저·사이트 주소로 수정 화면을 다시 열면 정리 재시도를 안내한다. 업로드 재사용 정보와 선택한 `File`은 메모리에만 보관한다.

정리 재시도는 최신 DB 스냅샷을 확인하고 현재 프로필·피드가 참조하는 경로를 제외한 뒤 100개씩 Storage API로 삭제한다. 조회가 실패하면 삭제하지 않고 대기 기록을 유지한다. 저장소 접근이나 기록 보관이 실패하면 화면에서 안내하며 메모리의 재시도는 유지한다. 브라우저 데이터를 지우거나 다른 기기·사이트 주소를 사용하면 해당 기록은 복구되지 않는다.

## 편집 내용 보호

로그인 상태를 다시 확인하는 중이거나 통신 오류가 발생하면 입력 내용과 선택한 파일을 유지하고 저장·업로드·정렬을 잠근다. `다시 확인`으로 인증 확인을 재시도하고, 세션이 만료되면 `다시 로그인`으로 같은 편집 화면에서 이어서 작업한다. 처음부터 로그인하지 않은 사용자의 수정 화면 접근은 계속 차단한다.

미저장 변경이나 진행 중 작업이 있으면 화면 이동·뒤로가기·로그아웃 전에 확인한다. 취소하면 편집 내용과 현재 주소를 유지한다. 새로고침·탭 닫기는 브라우저의 기본 이탈 확인을 사용한다. 저장 성공 후에는 변경 여부가 초기화된다. 이 기능은 자동 저장이 아니며, 브라우저가 이탈 확인을 생략하거나 기기가 강제 종료되면 메모리의 편집 내용은 복구되지 않는다.

섹션과 피드는 한 번에 한 목록만 정렬할 수 있다. 마우스 활성화 대기 단계부터 잠금을 공유하며, 취소·종료·인증 확인에 따른 비활성화 시 해제한다. 로그인 창을 닫았다 다시 열면 비밀번호와 오류가 초기화되고, 로그인 요청 중에는 Escape·배경 클릭으로 닫지 않는다. 비밀번호 입력은 요청을 시작한 직후 비운다.

## 모달과 동작 줄이기

로그인·이미지 확대는 native `dialog.showModal()`로 표시하고 모달 바깥 클릭 또는 Escape로 닫는다. 모달 밖의 입력과 초점을 차단하며 Tab·Shift+Tab을 내부에서 순환시킨다. 열기 전 초점과 스크롤 위치·기존 스타일을 복원하고, 중첩 모달은 마지막 모달이 닫힐 때 배경 스크롤을 해제한다. 로그인 중에는 Escape·배경 클릭을 모두 잠근다.

전역 `transition: all`을 제거하고 필요한 색상·테두리·불투명도·변형만 전환한다. `prefers-reduced-motion: reduce`에서는 애니메이션·전환과 부드러운 스크롤을 끄며 드래그 정렬의 인라인 전환도 덮어쓴다.

## 조회와 편집 상태

`src/hooks/useSiteQuery.ts`는 메인·수정 화면의 조회 상태, 재시도, 이전 요청 취소와 늦은 응답 무시를 담당한다. 표시 후 테마 복원 같은 화면 효과의 정리 함수도 요청 수명에 맞춰 실행한다.

`src/hooks/useSiteEditor.ts`는 DB 기준값과 초안, 변경 감지, 저장·정리·재조회, 섹션 추가와 초점, 이탈 보호와 목록 정렬 잠금을 담당한다. 페이지는 입력 요소의 오류 표시와 화면 구성에 집중한다. 저장·정리 ref와 현재 초안 ref는 유지해 같은 틱의 중복·교차 실행과 오래된 이탈 판단을 막는다.

## 검증과 데이터 변환

`src/utils/siteDraft.ts`의 `validateSiteDraft`를 화면과 저장 서비스에서 함께 사용한다. 화면은 반환된 필드 위치와 메시지를 해당 입력 요소의 `setCustomValidity`·`reportValidity`에 연결하고, 저장 서비스는 같은 규칙으로 네트워크 요청 전에 차단한다. 새 이미지의 형식·용량 검사는 기존 Storage 공통 검증을 거친다.

같은 파일의 `parseKeywords`, `toDraft`, `buildSaveData`는 키워드 파싱과 DB→편집 상태→저장 payload 변환을 담당한다. 이름·상태 메시지·제목·색상과 키워드는 기존 규칙대로 공백을 정리하고 섹션 본문의 서식 기호·줄바꿈·공백은 그대로 보존한다. 섹션·피드는 배열 순서와 DB ID를 유지하고, 새 항목은 null ID를 전달한다. 키워드는 기존의 위치별 ID 대응 규칙을 유지한다.

`src/utils/theme.ts`의 `themeFields`에 편집 키·DB 컬럼·CSS 변수·표시명을 정의하고 테마 편집·변환·미리보기에 함께 사용한다. Storage 파일명 해석은 Supabase에 의존하지 않는 `src/utils/imageFileName.ts`에 둔다. 변환 함수는 편집 상태나 선택한 `File`을 변경하지 않는다.

## 섹션 내용 서식

섹션 내용은 다음 문법으로 작성한다. 서식은 메인 화면의 섹션 내용에 적용하며, 제목·프로필 문구·키워드는 입력한 텍스트로 표시한다. 편집 화면의 textarea에서는 원문을 그대로 수정한다.

| 입력 | 표시 |
|---|---|
| `*볼드체*` | 굵은 글씨 |
| `_밑줄_` | 밑줄 |
| `/이탤릭체/` | 기울임 |
| `-가로줄-` | 글자 가운데 취소선 |

표는 각 줄의 시작과 끝에 `|`를 두고, 칸 사이도 `|`로 구분한다. 한 줄짜리 `| 표 |`도 표로 표시한다. 두 번째 줄에 구분선을 넣으면 첫 줄을 제목 행으로 표시하며, 표 안에서도 글자 서식을 사용할 수 있다.

```text
| 항목 | 내용 |
| --- | --- |
| 이름 | *캐릭터 이름* |
| 소개 | _밑줄_과 /이탤릭체/ |
```

기호를 그대로 표시하려면 앞에 역슬래시를 붙인다. 예를 들어 `\*별표\*`는 별표를 포함한 텍스트로, 표 안의 `\|`는 칸을 나누지 않는 세로줄로 표시한다. 닫는 기호가 없는 문구와 HTML 태그는 텍스트로 표시한다. 넓은 표는 표 영역 안에서 가로로 스크롤할 수 있다.

## 빌드와 검사

```cmd
npm run build
npm run lint
npm test
npm run test:editor:browser
npm run test:security:browser
```

Node.js 22.12 이상을 사용한다. `npm test`는 서식 파서 28개, 편집 변경 감지·목록 잠금 10개, 저장·정리 서비스 32개, 정리 기록 16개, 업로드 제한 12개, 조회 서비스 13개, 공통 검증·변환 18개의 검사를 실행한다. 각각 `test:format`, `test:editor`, `test:services`로 따로 실행할 수도 있다.

`npm run test:services`는 Supabase 경계만 모킹하고 실제 저장·Storage 코드를 실행한다. 업로드→DB 저장→기존 이미지 정리 순서, 정렬만 저장, 부분 업로드 실패, 응답 유실 후 업로드 경로 재사용, 충돌 시 편집 내용 보존, 정리 실패와 재시도를 검사한다. Vitest는 실제 `.env` 파일을 읽지 않는다.

`npm run test:editor:browser`는 테스트 서버와 실제 SDK를 사용하는 브라우저 회귀 검사 117개를 실행하며 실제 Supabase 프로젝트나 비밀번호는 사용하지 않는다. 단일 조회·연속 재시도·지연 응답 취소, 같은 틱의 저장·정리 중복과 교차 실행 차단, 용량 경계·피드 개수 제한과 원본 바이트 보존도 검사한다. 공통 검증·변환 외에 모달·동작 줄이기·정리 기록 복구와 재참조 보호도 확인한다. 1단계만 검사하려면 `node tests/editor.browser.mjs --phase1`을 실행한다. Chrome/Chromium이 필요하며 Windows·macOS·Linux의 기본 설치 경로를 찾는다. 다른 경로는 `CHROME_PATH` 환경변수로 지정한다. 전체 실행은 3분 안에 종료하며 테스트 서버·브라우저·임시 파일을 정리한다.

`npm run test:security:browser`는 가짜 설정으로 임시 프로덕션 빌드를 만들고 `vercel.json`의 헤더를 적용한 로컬 서버에서 29개 보안 검사를 실행한다. 정상 로그인·API·폰트 CDN CSS·이미지·blob 미리보기와 inline·eval·외부 스크립트·통신·프레임 차단을 확인한다. Supabase·CDN 응답은 브라우저에서 대체하며 실제 계정·DB에 접근하지 않는다. 실제 Vercel 배포 검증과는 구분한다.

`.github/workflows/ci.yml`은 각 브랜치의 push와 `main` 대상 PR, 수동 실행에서 `npm ci`, 린트, 단위 검사, 빌드, 브라우저·프로덕션 CSP 검사를 실행한다. Ubuntu와 Node.js 22를 사용하며 별도의 Supabase 환경변수나 GitHub Secrets는 필요하지 않다. 원격 CI 결과는 커밋을 푸시한 뒤 확인한다.

DB 회귀 검사는 `supabase/save.test.sql`을 프로젝트 소유자 권한으로 실행한다. 모든 콘텐츠 변경은 마지막에 롤백하며, 자동증가 ID 번호에는 간격이 생길 수 있다. 관리자 전용 실행 권한, 원자적 저장, 재시도와 충돌, Storage 정책·버킷 제한, 피드 50장 경계와 기존 초과 목록의 보존·교체·감축을 검사한다.

조회 DB 검사는 `supabase/read.test.sql`을 같은 권한으로 실행한다. 익명·비관리자 읽기 전용 호출, 함수 권한·RLS, 정렬·ID·원문 보존, 빈 목록과 1,005개 섹션 반환을 검사하고 롤백한다. 실제 DB 동시 커밋 부하 검사는 별도로 수행하지 않았다.

## 파일 정리 운영

응답이 불명확한 DB 요청의 새 업로드는 삭제 후보 기록에 넣지 않는다. 이후 사용되지 않는 파일이 남으면 프로젝트 소유자 권한으로 `supabase/storage-audit.sql`을 실행해 생성·수정 후 24시간이 지났고 현재 DB에서 참조하지 않는 경로를 확인한다. 이 SQL은 읽기 전용이며 실제 미참조 시작 시각을 추적하는 것은 아니다.

후보를 정리할 때는 편집 내용을 저장하고 결과를 확인한 뒤 모든 편집 탭과 진행 중 요청을 종료한다. 최신 DB 참조를 다시 확인하고 검토한 파일만 Storage 화면 또는 SDK `remove()`로 삭제한다. 24시간 경과만으로 자동 삭제하지 않으며 `storage.objects`를 SQL로 삭제하지 않는다. [공식 삭제 안내](https://supabase.com/docs/guides/storage/management/delete-objects)

DB와 Storage 삭제는 하나의 트랜잭션이 아니다. 직접 SQL로 이미지 경로를 복원하거나 파일을 교체할 때도 진행 중 편집·정리를 종료하고 대상 경로를 확인한다. 브라우저 기록은 실패한 정리를 재시도하기 위한 것이며 서버의 전체 파일 이력이나 주기적 삭제 작업을 대신하지 않는다.

## Vercel 배포 보안

프로젝트 루트의 `vercel.json`에 CSP·MIME 스니핑 방지·프레임 삽입 차단·Referrer-Policy·Permissions-Policy를 설정했다. `/edit`, `/manage.html`의 직접 접근은 `index.html`로 연결하고 앱에서 인증을 확인한다. 현재 Git 저장소 루트에 `package.json`이 있으므로 Vercel Root Directory는 `.`(기본값)이다. [공식 설정 안내](https://vercel.com/docs/project-configuration/vercel-json)

CSP는 앱 스크립트를 같은 출처에서만 허용한다. React의 스타일 속성에 필요한 인라인 CSS와 Pretendard CDN만 허용하고, 통신·이미지의 외부 출처는 현재 Supabase 프로젝트로 제한했다. Supabase URL·커스텀 도메인·외부 리소스를 변경하면 CSP 허용 출처도 함께 갱신해야 한다. 이 정책은 외부 iframe 삽입과 Vercel Toolbar 같은 외부 스크립트도 차단한다.

실제 배포는 별도로 진행한다. 배포 후 `curl.exe -I https://YOUR-SITE.vercel.app/edit`로 위 헤더를 확인하고 메인 이미지·폰트·로그인·새 이미지 미리보기·저장과 `/edit` 직접 진입·새로고침을 확인한다. HTTPS·배포 접근 보호·Auth 요청 제한 등 플랫폼 설정은 저장소의 JSON만으로 검증되지 않으므로 운영 계정에서 함께 확인한다. 로컬 개발 서버에는 Vercel 응답 헤더가 적용되지 않는다.

## 원격 저장소

- `origin`은 기본 저장소다. [원본 저장소](https://github.com/3rd-hargreaves/proflieManage)
- `backup`은 백업 저장소다. [백업 저장소](https://github.com/blank09114/proflieManage)

로컬 Git 저장소에 `origin`과 `backup` 원격을 등록했다. 작업 브랜치를 각 원격에 별도로 푸시한다.

## 브랜치 전략

1. `main`에 직접 커밋하거나 푸시하지 않는다.
2. 기능명이 드러나는 작업 브랜치를 만든다. 브랜치명 예시는 `react-migration`, `admin-auth`, `feed-sort`다.
3. 코드와 문서를 작업 브랜치에서 수정하고 커밋한 뒤 해당 브랜치를 원격으로 푸시한다.
4. 작업 브랜치에서 `main`을 대상으로 PR을 생성한다.
5. 변경사항과 필요한 검증 결과를 확인하고 PR을 통해 `main`에 병합한다.
6. 다음 작업은 최신 `main`을 기준으로 새 브랜치를 만들어 시작한다.

`backup`에도 같은 규칙을 적용한다. 백업할 작업 브랜치를 별도로 푸시하고 `main` 반영은 PR을 통해 진행한다.

이 문서의 작업 규칙과 GitHub 브랜치 보호 설정은 별도로 관리한다. 보호 설정의 적용 여부는 저장소에서 확인한다.

## 구현 방향

- 메인 `/`와 수정 `/edit` 두 페이지로 구성한다.
- 관리자 이메일은 고정하고 비밀번호만 입력받아 Supabase Auth로 로그인한다.
- 프로필·섹션·키워드·피드 순서·테마는 Supabase DB에서 관리한다.
- 이미지는 Supabase Storage의 `profile/`, `feed/` 경로에 저장한다.
- 이미지 확대·스와이프를 구현한다.
- 테마색은 CSS 변수에 적용하고 메인 페이지 제목은 캐릭터 이름과 연동한다.
- 프런트엔드는 Vercel에 배포한다.
